## Що саме демонструє проєкт

Проєкт показує типовий ланцюжок роботи інженера з автоматизації тестування:

1. Взяти **план тесту**: що налаштувати, що виміряти, скільки разів і які
   значення вважати прийнятними.
2. Налаштувати джерело сигналу через команди, подібні до команд реальних
   програмованих приладів.
3. Зняти кілька показів вимірювача потужності.
4. Відокремити справжнє відхилення величини від проблеми зв'язку з приладом.
5. Прийняти один з трьох вердиктів: `PASS`, `FAIL` або `INCONCLUSIVE`.
6. Зберегти достатньо даних, щоб інша людина могла зрозуміти рішення і
   відтворити програмний прогін.

Предметна історія навмисно проста: віртуальний генератор задає частоту й
потужність, а віртуальний вимірювач повертає **пряму** та **відбиту**
потужність. Це близько до мови RF/мікрохвильових систем, але не претендує на
фізично точну модель такого обладнання.

## Швидка картина: як проходить один тест

```text
plans/nominal.json
        │  параметри, межі, кількість показів, повтори
        ▼
CLI (командний рядок)
        ▼
runner ──► driver-и ──► SIM:: ресурси ──► віртуальний генератор / вимірювач
   │                                                    │
   │                                    синтетичні покази, шум, несправності
   ▼                                                    │
evaluation ◄───────────────────────────────────────────┘
   │
   ▼
JSON-звіт + Markdown-підсумок
```

Нижче — той самий процес людською мовою.

1. Користувач запускає CLI та обирає JSON-план, профіль симуляції і `seed`.
   `Seed` — початкове число для псевдовипадкової послідовності; однаковий seed
   дає однаковий синтетичний шум.
2. `runner` створює віртуальний стенд і відкриває два локальні ресурси:
   `SIM::RFGEN::INSTR` та `SIM::POWERMETER::INSTR`.
3. Драйвер генератора передає частоту й задану потужність, потім вмикає вихід.
4. Для прямої потужності runner запитує стільки показів, скільки задано у
   `readings` (у прикладі — п'ять). Потім так само запитує відбиту потужність.
5. Для кожної величини обчислюється звичайне арифметичне середнє та
   порівнюється з межами плану.
6. Якщо відповідь приладу сталася некоректною або не надійшла, runner не
   видає фальшивий `FAIL`: він повторює операцію за політикою `retries`, а при
   вичерпанні спроб фіксує `INCONCLUSIVE`.
7. Навіть за помилки ресурси закриваються. У реальному стенді це частина
   дисципліни коректного завершення сесій; тут це перевірювана властивість
   програмної моделі.

## Будова системи та роль кожного компонента

### Карта файлів

| Компонент | Файл або каталог | Відповідальність | Чому він виділений окремо |
| --- | --- | --- | --- |
| Точка запуску | `src/virtual_test_bench/cli.py` | Читає аргументи командного рядка, запускає план, створює звіти. | Інтерфейс користувача не змішується з тестовою логікою. |
| Модель даних | `models.py` | Описує план, межі та можливі вердикти типізованими структурами Python. | Один словник понять для всіх шарів; менше «магічних» рядків і чисел. |
| Перевірка плану | `testplan.py` | Перетворює JSON на `TestPlan`, відхиляє відсутні, нечислові, нескінченні або нелогічні значення. | Некоректний план треба зупинити до керування приладами. |
| Драйвери | `drivers.py` | Перекладає методи Python на текстові команди та перетворює відповідь вимірювача на число. | Runner не мусить знати синтаксис команд; реальний драйвер легше замінити. |
| Симулятор | `simulation.py` | Зберігає стан генератора, вимірювача, шум, профілі несправностей і локальні ресурси. | Фізична поведінка та помилки ізольовані від правил прийняття рішення. |
| Оркестратор | `runner.py` | Виконує setup → вимірювання → повтори → teardown; накопичує дані спроб. | Це місце, де тест стає послідовним, відтворюваним процесом. |
| Оцінювання | `evaluation.py` | Обчислює середнє, застосовує межі та guard band, формує вердикт. | Правило `PASS`/`FAIL` не повинно бути заховане в драйвері чи звіті. |
| Звітування | `reporting.py` | Записує повний JSON і короткий Markdown-підсумок. | Машина й людина отримують дані у зручних, окремих формах. |
| Винятки | `errors.py` | Визначає помилки на кшталт timeout або некоректної відповіді. | Помилка I/O чітко відрізняється від поганого виміряного значення. |
| Приклад плану | `plans/nominal.json` | Номінальні налаштування й правила прийняття. | Дані тесту можна змінювати без редагування коду. |
| Автотести | `tests/` | Перевіряють модулі й повний сценарій. | Доказують, що поведінка не зламається після змін. |
| Документація | `docs/` | Пояснює дослідження, протокол, дизайн, приклади звітів і цей посібник. | Код не має бути єдиним джерелом знань. |

### Межі відповідальності — чому вони важливі

У невеликій програмі можна було б помістити все в один файл: і команди,
і випадкові числа, і межі, і друк результату. Це швидко на старті, але погано
масштабується. Наприклад, щоб замінити симулятор на реальний прилад, довелося
б торкнутися правил `PASS`/`FAIL`; щоб змінити формат звіту — ризикувати
вимірюванням. Тут цього уникнуто:

- драйвер відповідає на питання «як поговорити з приладом?»;
- симулятор — «яку відповідь або несправність прилад начебто дає?»;
- runner — «у якому порядку виконується тест?»;
- evaluator — «що означає отримане число щодо вимоги?»;
- reporter — «як зберегти й показати вже ухвалене рішення?».

У **реальному стенді** на місці `simulation.py` був би адаптер до фізичного
інструмента (наприклад, PyVISA), а замість `SIM::...` — адреса приладу на GPIB,
послідовному порту або LAN. Водночас runner, evaluator і reporter повинні
залишитися майже без змін — саме це є цінністю поділу на шари.

## Тестування — центральна частина проєкту

### Два значення слова «тест»

У проєкті є два різні, але пов'язані види тестування.

1. **Віртуальний вимірювальний тест** — сценарій, який перевіряє поведінку
   умовного генератора за планом. Саме він формує `PASS`/`FAIL`/`INCONCLUSIVE`.
2. **Автоматизований тест програмного коду** — перевірка `pytest`, яка
   підтверджує, що симулятор і правила виконуються саме так, як задумано.

Перший імітує роботу виробничого або лабораторного стенда. Другий захищає сам
автоматизований стенд від програмних регресій. Без другого не можна впевнено
довіряти першому: скрипт може помилково інтерпретувати правильний показ як
неправильний або навпаки.

### Як влаштований віртуальний вимірювальний тест

План `plans/nominal.json` описує один тест. Його зміст у спрощеному вигляді:

```json
{
  "frequency_hz": 13560000,
  "power_setpoint_w": 100,
  "readings": 5,
  "limits": {
    "forward_power_w": {"lower": 95, "upper": 105},
    "reflected_power_w": {"upper": 5}
  },
  "guard_band_w": 0,
  "retries": 1
}
```

#### Крок 1. Валідація ще до початку вимірювання

Програма перевіряє, що частота та задана потужність є скінченними додатними
числами; кількість показів — додатне ціле; число повторних спроб і guard band
— не від'ємні; нижня межа не перевищує верхню. Це важливо, бо в реальному
стенді неправильні дані можуть означати неправильне налаштування обладнання.
У цій симуляції це насамперед захист коректності сценарію.

#### Крок 2. Setup: налаштування стану

Драйвер генератора надсилає команди, еквівалентні за наміром до:

```text
SOUR:FREQ 13560000
SOUR:POW 100
OUTP ON
```

**У симуляції:** команди просто записують числа та стан `output_on` в пам'ять.

**У реальному стенді:** контролер передав би байти по конкретному інтерфейсу;
прилад міг би застосовувати налаштування із затримкою, мати свій формат одиниць
і повертати власні коди помилок. Часто потрібні також очікування готовності,
синхронізація тригерів та перевірка статус-регістрів.

#### Крок 3. Серія показів

Runner збирає п'ять окремих значень прямої потужності, а потім п'ять значень
відбитої. Замість рішення за одним числом він використовує середнє:

\[
\bar{x} = \frac{x_1 + x_2 + \ldots + x_n}{n}
\]

де `x₁ … xₙ` — окремі покази, а `n` — їхня кількість.

Це не робить модель метрологічно повною, але вчить важливого принципу:
вимірювання змінюються, тому один випадковий показ рідко є достатньою основою
для рішення.

**У реальному стенді** план відбору даних був би окремим інженерним рішенням:
кількість показів, затримка між ними, час стабілізації, смуга пропускання
вимірювача, усереднення в самому приладі та спосіб відбракування аномалій
визначаються вимогою, ризиком і характеристиками обладнання.

#### Крок 4. Оцінювання

Якщо середнє прямої потужності нижче 95 W або вище 105 W, це `FAIL`. Якщо воно
у межах — `PASS`, якщо не діє guard band. Для відбитої потужності встановлено
лише верхню межу 5 W: від'ємна відбита потужність у моделі не генерується, а
менше значення тут вважається кращим.

Важлива відмінність:

- правильна числова відповідь, але за межами вимоги → `FAIL`;
- немає надійної числової відповіді через timeout або текст замість числа →
  `INCONCLUSIVE`.

`FAIL` означає: вимірювання відбулося, і результат не задовольняє правило.
`INCONCLUSIVE` означає: система не має достатніх валідних даних, щоб чесно
зробити висновок.

#### Крок 5. Teardown: коректне завершення

У блоці `finally` runner вимикає вихід, якщо він був увімкнений, і закриває
обидва ресурси. `finally` у Python виконується навіть тоді, коли в середині
процесу виник виняток.

**У реальності:** така послідовність могла б також встановлювати безпечний
стан приладу, розривати сесію, зберігати журнал і звільняти спільний ресурс.
Але саме цей проєкт не може і не повинен вважатися реалізацією реальної
функціональної безпеки.

### Що саме перевіряє `pytest`

Набір автотестів покриває як дрібні правила, так і повний шлях від плану до
звіту. Серед основних груп:

| Група | Приклад питання, на яке відповідає тест | Навіщо це потрібно |
| --- | --- | --- |
| Валідація плану | Чи відхиляються `NaN`, нескінченність, нульова частота, перевернуті межі? | Не допустити неоднозначного сценарію. |
| Транспорт і команди | Чи потрапляє невідома команда в чергу помилок? | Командний шар має передбачувану діагностику. |
| Симуляція | Чи однаковий seed відтворює однакові покази? | Тести не мають «флапати» через випадковість. |
| Оцінювання | Чи `FAIL` за виходом за межі й `INCONCLUSIVE` на межі guard band? | Вердикт — ключова бізнес-логіка. |
| Повтори | Чи після timeout виконуються рівно дозволені спроби? | Уникнути як раннього припинення, так і нескінченного циклу. |
| Часткові дані | Чи показ, отриманий перед збоєм, лишається у retry-діагностиці? | Діагностика повинна бути правдивою, а не змішувати дані різних величин. |
| Життєвий цикл | Чи закриваються ресурси після прогону? | Не накопичувати відкриті сесії. |
| Інтеграція | Чи номінальний, низькопотужний і timeout-сценарії дають очікувані вердикти? | Перевірити взаємодію всіх шарів. |
| Звітування | Чи створюються JSON та Markdown і чи зберігаються метадані? | Результат має бути доступним після завершення процесу. |

Ці перевірки навмисно використовують **детерміновані** профілі. У звичайному
випадковому тесті інколи трапляється успіх, а інколи помилка без зміни коду —
такий тест називають нестабільним або *flaky*. Для інженерного інструмента це
дуже погано: команда перестає довіряти автоматизації. Seed і явні профілі
несправностей дають повторюваний доказ поведінки.

### Чому обрано `pytest`

`pytest` — легкий і поширений тестовий фреймворк Python. Він підходить тут,
бо дозволяє коротко описувати перевірки, має читабельні повідомлення про
падіння тесту та підтримує ізоляцію через fixtures/monkeypatch там, де це
необхідно. Не потрібні ані сервер, ані база даних, ані спеціальне лабораторне
ПЗ: перевірки виконуються локально і в CI (безперервній інтеграції).

### Чого автотести не доводять

Зелені програмні тести доводять, що *модель виконує закладені правила*. Вони
не доводять, що реальний вимірювач відкалібрований, що кабель справний, що
справжній генератор безпечний або що фізичний виріб відповідає специфікації.
Це різні рівні доказів.

## Величини, що вимірюються

### Частота

**Частота** — кількість повторень коливання за секунду. Її одиниця — герц
(`Hz`). У плані використано `13 560 000 Hz`, тобто `13.56 MHz` (мегагерца,
мільйона герців).

**У симуляції:** частота є збереженим параметром; вона не впливає на
математичну модель показів.

**У реальності:** частота може змінювати точність генератора, втрати в кабелі,
чутливість датчика, узгодження навантаження й допустимі режими обладнання.
Її вимірювання/перевірка вимагало б придатного лічильника частоти, аналізатора
або внутрішньої референсної системи приладу, з власними похибками.

### Задана потужність (setpoint)

**Setpoint** — значення, яке контролер наказує приладу встановити. У прикладі
це `100 W` (ват). Це не тотожне незалежно підтвердженій фактичній потужності.

**У симуляції:** setpoint одразу стає базою для синтетичних показів.

**У реальності:** реальна вихідна потужність може відрізнятися через точність
генератора, режим, температуру, навантаження, кабелі, роз'єми і спосіб
вимірювання. Саме тому тест зазвичай порівнює незалежний показ вимірювача з
вимогою, а не просто довіряє setpoint.

### Пряма потужність

**Пряма потужність** (`forward power`) — у спрощеному описі потік потужності
від джерела до навантаження. Її одиниця — ват (`W`). Вона є головною величиною
в цьому прикладі: середнє п'яти показів повинно потрапити в діапазон 95–105 W.

**У симуляції:**

- `nominal` генерує значення поблизу заданої потужності;
- `power_low` застосовує коефіцієнт `0.90`, тобто близько 90 W для setpoint
  100 W;
- `meter_offset` додає постійні синтетичні +2 W;
- `warmup` піднімає коефіцієнт від 0.80 до 1.00 для перших трьох показів;
- шум обмежений приблизно ±0.2 W і відтворюється з seed.

**У реальності:** пряму потужність часто знімають датчиком потужності,
спрямованим відгалужувачем або ватметром. На результат впливають частота,
динамічний діапазон, рівень, тип датчика, втрати тракту, узгодження,
температура, калібрування та час усереднення приладу.

### Відбита потужність

**Відбита потужність** (`reflected power`) — частина енергії, яка через
неідеальне узгодження навантаження повертається у напрямку джерела. Високе
значення часто є сигналом проблеми з навантаженням або трактом.

**У симуляції:** зазвичай це 2% від setpoint; для `load_mismatch` — 10%.
Якщо синтетичне відбите значення більше 5 W, модель вимикає `output_on` — це
**віртуальний interlock**, програмна умова для демонстрації fault handling.

**У реальності:** відбита потужність пов'язана з комплексним опором,
коефіцієнтом відбиття, частотою, кабельним трактом та режимом джерела. З неї
можуть обчислювати VSWR або return loss, але цей проєкт цього не робить. Реальні
захисти генератора можуть бути швидкими апаратними/прошивковими механізмами;
віртуальний interlock тут не є аналогом безпеки.

## Метрологія: що треба враховувати

Метрологія — наука і практика вимірювань. Головна помилка новачка — вважати
виведене приладом число безумовною істиною. Реальний результат — це число,
умови його отримання, метод, прилад та оцінка надійності.

### Вимірювана величина і результат

**Вимірювана величина** (*measurand*) — чітко визначене «що саме ми хочемо
дізнатися». Не просто «потужність», а, наприклад: «пряма RF-потужність на
виході конкретного порту при 13.56 MHz, установленому режимі й зазначеному
навантаженні». Якщо умови не записані, два однакові на вигляд числа можуть
означати різні речі.

У цьому проєкті measurand спрощено до `forward_power` або `reflected_power` у
ватах за конфігурації плану. Це достатньо для демонстрації програмного
ланцюжка, але не повна специфікація реального вимірювання.

### Повторюваність, шум і середнє

**Повторюваність** — близькість результатів, коли той самий об'єкт вимірюють
за однакових умов коротким рядом. Випадковий розкид називають шумом або
випадковою складовою. Серія показів і середнє часто зменшують вплив випадкової
складової на оцінку центрального значення.

Але середнє не лікує все: якщо прилад зміщений, кабель має невраховані втрати
або система ще прогрівається, усі покази можуть бути дуже схожими й водночас
неправильними. Тому «п'ять однакових чисел» не дорівнює «правильне число».

### Випадковий і систематичний вплив

| Вид впливу | Інтуїтивно | У симуляції | У реальному вимірюванні |
| --- | --- | --- | --- |
| Випадковий | Покази трохи коливаються то вище, то нижче. | Seeded noise ±0.2 W. | Шум електроніки, короткочасна нестабільність джерела, обмеження відліку. |
| Систематичний | Покази стабільно зсунуті в один бік. | `meter_offset` додає +2 W. | Некоректна калібровка, втрати, частотна характеристика, нульове зміщення. |
| Часовий | Значення змінюється після старту або з часом. | `warmup` — задана крива перших показів. | Тепловий режим, дрейф, стабілізація генератора чи датчика. |

### Похибка не дорівнює невизначеності

**Похибка вимірювання** — різниця між результатом і істинним значенням.
Проблема в тому, що істинне значення зазвичай невідоме, тому похибку не можна
просто «побачити» в одному реальному вимірюванні.

**Невизначеність вимірювання** — кількісна оцінка розсіювання значень, яке
можна обґрунтовано приписати результату. Вона може містити статистичні внески
від повторів (**Type A**) та внески з інших джерел — специфікацій, сертифікатів
калібрування, роздільної здатності, моделей (**Type B**).

Цей проєкт **не розраховує невизначеність** і не створює бюджет
невизначеності. Відображений offset і шум — лише наочні сценарії для
програмного тестування. Перетворювати їх на реальну заяву на кшталт «100 W ±
0.2 W» було б неправильно.

### Калібрування і метрологічна простежуваність

**Калібрування** встановлює співвідношення між показом приладу та значенням,
отриманим за еталоном у визначених умовах. **Простежуваність** означає
документований, неперервний ланцюг порівнянь до визнаних еталонів, де кожна
ланка робить свій внесок у невизначеність.

**У симуляції:** немає ані еталона, ані калібрувального сертифіката, ані
простежуваності. JSON-звіт є простежуваним як *програмний журнал* (видно,
які дані й правила застосовано), але не метрологічно простежуваним.

**У реальності:** треба знати чинність калібрування кожного приладу й
аксесуара, умови застосування сертифіката, невизначеність калібрування,
інтервал перекалібрування та стан кабелів/перехідників/датчиків.

### Межі специфікації, tolerance та guard band

**Межа специфікації** або **tolerance** — вимога до виробу чи тесту. У плані
95–105 W — це допустимий інтервал, а не інтервал невизначеності.

**Guard band** — звуження зони прийняття: нижня межа рухається вгору, верхня —
вниз. Наприклад, за меж 95–105 W і guard band 1 W ефективне безумовне «PASS»
вікно стає 96–104 W. Результат 95.5 W формально всередині специфікації, але
надто близько до неї за правилом цього проєкту, тому буде `INCONCLUSIVE` з
причиною `guard-band boundary`.

У реальному прийнятті продукції guard band обирають не довільно. Він пов'язаний
з ризиком помилково прийняти невідповідний виріб (**consumer risk**) або
помилково відхилити відповідний (**producer risk**), із невизначеністю методу
та узгодженим правилом рішення. Тут guard band — навчальна демонстрація цієї
ідеї, а не затверджене правило відповідності.

## Як працює симуляція і як це відрізняється від реальності

### Профілі поведінки

Профіль — це явно обраний сценарій. За незмінного `seed` він відтворюваний.

| Профіль | Що робить код | Як це можна інтерпретувати в реальному світі | Вердикт у моделі |
| --- | --- | --- | --- |
| `nominal` | Повертає близькі до setpoint покази з малим шумом. | Нормальна стабільна робота. | Зазвичай `PASS`. |
| `power_low` | Множить пряму потужність на 0.90. | Недостатня вихідна потужність; причина не моделюється. | `FAIL`. |
| `meter_timeout` | Кожен вимірювальний запит завершується timeout. | Збій з'єднання, приладу або очікування відповіді. | `INCONCLUSIVE` після повторів. |
| `malformed_reply` | Повертає текст, який не можна перетворити на число. | Некоректна відповідь, неправильний режим/протокол, зіпсовані дані. | `INCONCLUSIVE`. |
| `meter_offset` | Додає сталі +2 W. | Можливе зміщення показів; не діагностує причину. | Залежить від меж. |
| `warmup` | Перші значення нижчі, далі досягають setpoint. | Умовна стабілізація після ввімкнення. | Залежить від середнього й меж. |
| `load_mismatch` | Відбита потужність — 10%, після >5 W вимикається output. | Неузгоджене навантаження; реальна фізика значно складніша. | `INCONCLUSIVE` для перерваного виміру; часткові дані збережено. |

### Що тут фізично спрощено

Відбита потужність тут не обчислюється з повноцінної RF-моделі. Немає
комплексного опору, фази, S-параметрів, коефіцієнта відбиття, стоячої хвилі,
частотної залежності, гармонік, втрат кабелю або теплової моделі. Коефіцієнти
2% і 10% — програмні параметри для отримання зрозумілих гілок тесту.

Це свідомий компроміс. Мета — показати надійну архітектуру автоматизації:
команди, стан, збої, повтори, рішення та звіти. Фізично правдоподібна RF-модель
була б окремим складним проєктом і створила б ризик неправдивої претензії на
інженерну точність.

### Чому необхідний seed

Python генерує тут **псевдовипадкові** числа: вони виглядають випадковими,
але є детермінованою послідовністю. `seed=42` означає: «почни цю послідовність
у визначеній точці». Тому помилку можна повторити локально, у CI й на іншому
комп'ютері. У реальних вимірюваннях шум не можна «перезапустити з seed»;
натомість фіксують умови, час, конфігурацію, серійні номери, калібрування та
сирі дані.

## Команди, зв'язок і протоколи

### SCPI-подібні команди

SCPI (Standard Commands for Programmable Instruments) — поширена текстова
мова команд для програмованих приладів. У проєкті реалізовано лише маленький
**SCPI-подібний** набір; це не сумісна реалізація SCPI чи IEEE 488.2.

| Команда | Призначення в моделі |
| --- | --- |
| `*IDN?` | Повертає ідентифікаційний рядок віртуального ресурсу. Знак `?` означає запит відповіді. |
| `*CLS` | Очищає локальну чергу помилок. |
| `SOUR:FREQ <Hz>` | Задає частоту генератора. |
| `SOUR:POW <W>` | Задає потужність генератора. |
| `OUTP ON` / `OUTP OFF` | Вмикає/вимикає віртуальний вихід. |
| `MEAS:POW?` | Повертає один синтетичний показ прямої потужності. |
| `MEAS:REFL?` | Повертає один синтетичний показ відбитої потужності. |
| `SYST:ERR?` | Повертає найстарішу помилку в черзі, або `0,"No error"`. |

Невідома команда додає `-113,"Undefined header"` у FIFO-чергу (first in,
first out — «першим прийшов, першим вийшов»). Це показує важливу ідею:
помилка команди може існувати в стані приладу і її слід свідомо прочитати.

### VISA, PyVISA та транспорт

VISA (Virtual Instrument Software Architecture) — стандартний програмний
інтерфейс, який у реальних системах дає однакову модель ресурсу для різних
способів зв'язку. PyVISA — Python-бібліотека, що працює поверх реалізації VISA
або сумісного backend.

У коді є лише схожа форма: менеджер відкриває локальні `SIM::...` ресурси, а
драйвер викликає `write()`, `query()` та `close()`. Це вигідно для навчання:
видно типовий контракт без встановлення драйверів чи підключення обладнання.

**У реальності** адреси могли б виглядати так:

- `GPIB0::10::INSTR` — прилад з адресою 10 на шині GPIB;
- `ASRL1::INSTR` — послідовний порт;
- `TCPIP0::192.0.2.10::inst0::INSTR` — прилад через мережу.

GPIB — спеціалізована шина приладів, RS-232/serial — послідовний інтерфейс,
Ethernet/LAN — мережеве з'єднання. Цей проєкт не моделює їхні електричні рівні,
кадри, швидкості, мережеву безпеку чи затримки; timeout використано як
універсальний навчальний приклад проблеми I/O.

## Плани тестів, межі та вердикти

### Чому план є даними, а не кодом

План окремим JSON-файлом дозволяє інженерові змінити набір вимог без
редагування Python-логіки. Код знає *як* виконувати план, а план каже *що*
перевірити. Це зменшує ризик випадково змінити алгоритм разом із числом
допуску та полегшує рев'ю змін.

Поточна реалізація приймає **JSON**. У деякій документації згаданий YAML як
можливий формат читання людьми, але YAML-парсер у цій версії не реалізовано.
Не слід перейменовувати JSON на YAML або вважати їх взаємозамінними.

### Правила вердикту

| Умова | Вердикт | Причина |
| --- | --- | --- |
| Валідне середнє нижче нижньої межі | `FAIL` | `below lower limit` |
| Валідне середнє вище верхньої межі | `FAIL` | `above upper limit` |
| Валідне середнє всередині вихідних меж, але поза guard band | `INCONCLUSIVE` | `guard-band boundary` |
| Валідне середнє у всіх ефективних межах | `PASS` | `within limits` |
| Timeout або нечислова відповідь після всіх спроб | `INCONCLUSIVE` | Повідомлення про помилку та кількість спроб |

В evaluator немає «прихованої магії»: він застосовує арифметичне середнє і
порівняння з числовими межами. Будь-який розвиток до статистичних критеріїв,
зважених середніх, невизначеності або правил відбракування аномалій повинен
бути явно описаний у плані й протестований.

## Несправності, повторні спроби та діагностика

### Повтори (retries)

Значення `retries: 1` означає максимум дві спроби: первинну і одну повторну.
Повторюється тільки операція вимірювання конкретної величини, не весь тест.
Це розумна базова політика для перехідного timeout, але не універсальна
стратегія.

У реальному стенді перед повтором часто потрібні додаткові дії: очистити
статус, перевірити з'єднання, повторно налаштувати прилад, зачекати готовність
або зупинитися, якщо повтор може бути небезпечним. Політика повторів повинна
бути погоджена для конкретного обладнання, а не копіюватися механічно.

### Частковий набір даних

Якщо перший показ уже прийшов, а другий завершується timeout, перший показ не
зникає. Runner зберігає для кожної невдалої спроби номер `attempt`, список
вже зібраних `readings` і текст `error`. Це критично для діагностики: видно,
чи збій стався одразу, після одного правдоподібного числа або після майже
повної серії.

Ці часткові покази не використовуються для розрахунку фінального середнього
успішного вимірювання. Вони є діагностичними даними, оскільки серія не була
завершена за правилами плану.

### Практичне читання несправностей

| Симптом у звіті | Що він означає в цій моделі | Що перевіряли б у реальному стенді |
| --- | --- | --- |
| `simulated meter timeout` | Навмисно увімкнений профіль `meter_timeout`. | Кабель/мережу, адресу VISA, час timeout, стан приладу, журнал помилок. |
| `non-numeric instrument reply` | Профіль повернув текст замість числа. | Команду, режим приладу, розділювач, одиниці, протокол, помилки приладу. |
| `virtual interlock latched` | Симулятор вимкнув output після високої відбитої потужності. | Реальні журнали захисту та фізичний тракт; не покладатися на цю модель як на безпеку. |
| `above upper limit` | Валідне середнє перевищило межу плану. | Повторити за процедурою, перевірити умови й невизначеність, дослідити виріб. |

## Звіти та відтворюваність

Після прогону створюються два файли.

- `result.json` — повний машинно-читаний запис: план, seed, профіль, час,
  конфігурація симуляції, результати, сирі покази, середні, межі, вердикти та
  записи невдалих спроб.
- `summary.md` — коротка таблиця для людини: величина, середнє, вердикт,
  причина.

JSON важливіший для аудиту, бо Markdown навмисно стислий. Щоб повторити
симуляцію, потрібні щонайменше план, назва профілю й seed. У реальному
контексті до такого запису зазвичай додали б ідентифікатори приладів,
версії прошивок і драйверів, серійні номери, калібрувальний статус, умови
довкілля, топологію тракту, оператора та точний час.

Приклади всіх трьох типів результату містяться у
[`docs/examples/`](examples/): `pass.md`, `fail.md`, `inconclusive.md`.

## Що могло бути реалізовано і чому обрано цей варіант

### Вибір навчального сценарію

На етапі проєктування розглядалися три напрями.

| Варіант | Переваги | Недоліки | Рішення |
| --- | --- | --- | --- |
| DC-джерело + електронне навантаження | Простий для пояснення напруги/струму; менше RF-термінів. | Менш близький до RF/потужнісного контексту цільової ролі. | Не обрано. |
| RF-генератор + вимірювач потужності + навантаження | Показує частоту, пряму/відбиту потужність, interlock і стиль інструментального керування. | Легко перебільшити фізичну достовірність. | **Обрано**, але модель суворо спрощено. |
| Загальний DUT із цифровими входами/виходами | Універсальний, легко розширюється. | Менше демонструє специфіку вимірювального стенда. | Не обрано для першої версії. |

### Архітектурні альтернативи

| Альтернатива | Чому не обрано для v0.1.0 | Коли вона доречна |
| --- | --- | --- |
| Відразу PyVISA та фізичний прилад | Потребує обладнання, драйверів, дозволів і реальної процедури безпеки; це зруйнувало б hardware-free властивість. | Коли є конкретний стенд, перевірені адреси й відповідальність за його експлуатацію. |
| Повноцінний SCPI/VISA-емулятор | Великий обсяг стандартів не додає цінності головній меті. | Для суміснісного тестування бібліотеки або емулятора приладу. |
| Один монолітний скрипт | Швидко написати, важко тестувати й замінювати складові. | Лише для одноразового прототипу. |
| Випадкові fault-и без seed | Нібито «реалістичні», але неможливо стабільно тестувати. | Майже ніколи для базових автотестів; можуть знадобитися для окремого stress/fuzz-тесту. |
| Один вимір без серії | Простіший код, але демонструє гіршу вимірювальну практику. | Якщо специфікація приладу й вимога дійсно визначають одиничний вимір. |
| База даних, веб-інтерфейс, мікросервіси | Ускладнюють проєкт без покращення основного ланцюжка. | Коли потрібні багато стендів, користувачів, історія та доступ через мережу. |

### Чому цей баланс є корисним

Обрана реалізація достатньо мала, щоб її можна було прочитати цілком, але має
головні інженерні межі: дані плану, транспортний контракт, драйвери,
моделювання несправностей, оцінювання, протоколи звітності й автотести. Вона
демонструє не «досконалу фізику», а вміння будувати програмний процес, який
можна пояснити, перевірити і замінити по частинах.

## Обмеження та безпечне трактування результатів

Не можна робити такі висновки лише за результатом цього репозиторію:

- що реальний генератор або будь-який виріб відповідає специфікації;
- що система має відому похибку чи невизначеність;
- що вимірювальний тракт відкалібрований або метрологічно простежуваний;
- що віртуальний interlock забезпечує захист людини, обладнання чи RF-тракту;
- що команда сумісна з конкретним виробником, приладом, SCPI-діалектом або
  VISA-backend;
- що профілі `power_low`, `warmup` чи `load_mismatch` описують фізику
  справжнього пристрою.

Коректне формулювання результату: «За заданим JSON-планом і детермінованим
профілем ця *програмна симуляція* сформувала такий-то вердикт і зберегла дані,
які пояснюють це рішення».

## Словник термінів і скорочень

| Термін | Просте пояснення |
| --- | --- |
| Acceptance limit | Межа, за якою результат перестає відповідати правилу плану. |
| Backend | Нижній програмний шар, який виконує роботу з конкретним драйвером або транспортом. |
| CI | Continuous Integration, безперервна інтеграція: автоматичний запуск перевірок після змін коду. |
| CLI | Command-Line Interface, інтерфейс командного рядка. |
| DUT | Device Under Test, пристрій під тестом. У цьому проєкті це спрощена модель генератора/навантаження, а не реальний пристрій. |
| FIFO | First In, First Out: першим додали — першим прочитали. Принцип черги помилок. |
| Guard band | Додаткова зона обережності біля межі; звужує інтервал безумовного прийняття. |
| GPIB | General Purpose Interface Bus, традиційна шина зв'язку вимірювальних приладів; також IEEE 488. |
| Hz / MHz | Герц / мегагерц: одиниці частоти. 1 MHz = 1 000 000 Hz. |
| Interlock | Блокування роботи за певної умови. У цьому коді — лише віртуальна програмна умова, не захисна система. |
| I/O | Input/Output, введення/виведення: обмін даними програми з приладом або ресурсом. |
| JSON | Текстовий формат структурованих даних. У цьому проєкті ним записано план і повний звіт. |
| Measurand | Вимірювана величина, точно визначене «що саме вимірюємо». |
| Markdown | Простий текстовий формат розмітки; ним створюється читабельний підсумок звіту. |
| Noise | Шум, випадковий розкид показів. |
| Offset | Стале зміщення показів в один бік. |
| `PASS` | Дані валідні й відповідають ефективним межам плану. |
| `FAIL` | Дані валідні, але середнє значення виходить за межі плану. |
| `INCONCLUSIVE` | Недостатньо підстав для `PASS` або `FAIL`: наприклад, timeout, нечислова відповідь чи guard band. |
| PyVISA | Python-бібліотека для роботи з VISA-сумісними ресурсами. Тут вона не використовується напряму. |
| Random noise | Випадкове коливання, яке в моделі відтворюється за seed. |
| Repeatability | Повторюваність: близькість повторних результатів в однакових умовах. |
| Retry | Повторна спроба операції після перехідної помилки. |
| RF | Radio Frequency, радіочастота. У проєкті це лише контекст термінів, не реальний RF-стенд. |
| SCPI | Standard Commands for Programmable Instruments, поширений стиль текстових команд для приладів. Реалізовано лише навчальну підмножину, схожу за стилем. |
| Seed | Початкове число генератора псевдовипадкових чисел; забезпечує повторюваність симуляції. |
| Setpoint | Значення, яке контролер задає приладу; не гарантує незалежно виміряний фактичний результат. |
| Systematic effect | Постійна або передбачувана складова впливу, наприклад зсув калібрування. |
| Teardown | Етап завершення: вимкнення виходу, закриття ресурсів, прибирання стану. |
| Timeout | Перевищення часу очікування відповіді. Не є доказом того, що вимірювана величина «погана». |
| Tolerance | Допуск: дозволений діапазон значення за вимогою. |
| Traceability | У загальній мові — можливість простежити, звідки взялося рішення; у метрології — документований ланцюг до еталонів. У цьому проєкті є лише програмна traceability. |
| Uncertainty | Невизначеність вимірювання; не те саме, що похибка. У проєкті не обчислюється. |
| VISA | Virtual Instrument Software Architecture, API для доступу до приладів через різні інтерфейси. |
| W | Ват, одиниця потужності. |
